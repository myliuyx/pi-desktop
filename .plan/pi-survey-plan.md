# 梳理 Pi 的方案（pi-survey-plan）

> 制定日期：2026-09-22
> 背景：已完成 Pi 接入 POC（`.plan/poc-pi-2026-09-22.md`，四步全过，Electron 内真实会话跑通）。
> 下一步是写适配层，但**适配层的形状取决于 Pi 的事件模型**——不能凭想象开工。
> 本文档回答"怎么梳理 Pi"，不是梳理结果本身。
> 配套：`.plan/pi-integration-points.md`（替换点清单）、`docs/pi-agent-core-调研.md`（选型调研）

---

## 一、为什么先出方案，而不是直接开梳

`pi/` 是 **12 个包的 monorepo、1596 个文件**。而且 Pi 自身仍在演进：

- 版本 0.86.1，pre-1.0，npm 发布极频繁
- 内部重构未完成：`packages/agent/docs/mobile-handoff` 自述 7 个单元中只有 3 个有可用代码、
  4 个仅规格；`04-tool-output` / `05-assistant-output` 未实现
- 仓库自有类型检查基线约 788 个已有错误（属内部计划，不直接影响 SDK 使用）

**在这种状态下"通读 Pi"既不可能也不划算**——读完的部分可能明天就变。
正确做法是：**按"下一步要做什么决策"来反向界定要读什么**，每个阶段产出一个可验收的结论，
读够了就停。

## 三、包地图与相关性分级

先划清楚"哪些不必读"——这是控制工作量的关键。

| 包 | 相关性 | 说明 |
|---|---|---|
| `coding-agent` | **A 必读** | SDK 入口、事件、工具、扩展、RPC 协议。我们要对接的就是它 |
| `agent`（pi-agent-core） | **A 必读** | 事件模型、工具定义、钩子。Q1/Q3 的地基 |
| `ai`（pi-ai） | **A 必读（只读接口层）** | 统一的 LLM API 与流式事件类型；不需要读 provider 实现细节 |
| `durable` | **B 按需** | 会话 / 任务 / 文档的持久化运行时，Q2 相关 |
| `session-backends`（sqlite-node） | **B 按需** | 会话存储后端，Q2 相关 |
| `protocol` / `client` / `server` | **B 按需** | 传输层。三者自述 experimental、无兼容保证；**主进程直连方案可绕开它们** |
| `tui` | **C 不读** | 终端 UI 库，我们用 React 不用它。它只作为 native 依赖风险存在（POC 已验证可加载） |
| `chord` / `telemetry` / `evals` | **C 不读** | 内部基础设施，与对接无关 |

**不读 C 类，是这份方案最大的省力点。**

## 四、分阶段计划

| 阶段 | 要回答 | 主要读什么 | 产出 | 估时 |
|---|---|---|---|---|
| **S1** | Q1 事件模型与映射 | `coding-agent/docs/rpc.md`（事件类型全集）、`docs/sdk.md`、`examples/sdk/01..13` | **Pi 事件 → Block 映射表**：逐事件列出「对应哪种 Block / 需要哪些字段 / 流式如何增量更新」 | 4h |
| **S2** | Q2 会话与持久化 | `docs/sessions.md`、`docs/session-format.md`、`durable`、`session-backends` | 会话列举 / 加载 / 续接方案；`accept:m1/m2` 的 mock 会话去留决策 | 3h |
| **S3** | Q3 工具与授权 | `docs/extensions.md`（Extension UI Protocol：`select` / `confirm`）、`examples/extensions/*` | `TerminalCard` / `ApprovalCard` 的完整数据流（含授权应答的幂等语义） | 3h |
| **S4** | Q4 传输层选型 | `docs/rpc.md`、`protocol` / `client` / `server` 的 README | **同进程直连 vs 独立进程 + HTTP/SSE** 的决策与理由（含 Web 版怎么统一） | 3h |
| **S5** | Q5 自建能力 | `docs/usage.md`（明确列出不内置的能力）、`examples/extensions/custom-provider-*` | MCP / plan mode / to-dos 的补齐清单与每项成本 | 3h |
| **S6** | 汇总 | 前五阶段产物 | **《Pi 对接设计》**：适配层接口草案 + 分阶段落地顺序 + 验收策略 | 2h |

合计 **约 18h 净工时**（≈3 个工作日）。

### 顺序建议

- **S1 必须最先做**——它直接决定适配层形状，而适配层是下一步就开工的东西。
- **S4 要早于适配层落地定下来**（不必早于 S1 完成）：它决定 core 包的接口边界。
  调研文档已给出倾向（桌面走 IPC，后期 Web 走 SSE，UI 层禁止 import `node:*`），S4 只需把它坐实成接口。
- S2 / S3 / S5 可以按实际开工顺序往后排，不必一次做完。

## 五、方法与纪律（沿用本项目已验证有效的做法）

1. **先读 docs，必要时才读 src。** docs 是权威口径；只有 docs 说不清、或与实测矛盾时才进源码。
   **两者冲突时以实测为准。**
2. **所有结论标出处**（`文件:行号`），禁止凭记忆或凭上一轮会话的摘要写结论
   （本项目已多次因"凭摘要写期望值"出错，见 2026-09-22 日志）。
3. **对事件形状的断言必须用真实会话的 dump 验证**，不能只读文档。
   现成资产：`pi/_poc/smoke.ts` 与 `pi/_poc/electron-probe/`，随时可跑一次真实会话把事件打出来
   （火山方舟 key 已配好，`pi/_poc/.env.local`）。
4. **每阶段产一份 `.plan/survey/Sn-*.md`**，未复核前不并入主文档——避免半成品结论污染决策依据。
5. **与既有决策冲突时必须显式提出，不静默改。** 典型：若发现 Block 六型不足以表达 Pi 的某种事件，
   要停下来讨论改 `mock/types.ts`（UI 数据契约）的代价，而不是在适配层里偷偷塞字段。
6. **一次性只读一个阶段的范围**，读够了就停。梳理的目的是支撑决策，不是读完 Pi。

---

## 六、明确的边界（梳理期不做的事）

- 不读 C 类包（`tui` / `chord` / `telemetry` / `evals`）的源码
- 不改 `packages/ui` 的任何代码
- 不提前动手写适配层（等 S1 的映射表出来再写）
- 不升级 Pi 版本、不动 `pi/` 的源码（它是 gitignore 的上游 clone，需要时用官方命令还原）

---

## 七、验收

每个阶段结束时：

1. 产出文档中标了出处的关键结论 ≥1 条/问题
2. 涉及"事件形状 / 接口签名"的结论，附一次真实会话的实测证据（日志片段即可）
3. 明确写出"本阶段未覆盖什么"，避免下一个人误以为已经全覆盖

全部六阶段完成后，《Pi 对接设计》能直接指导适配层开工，才算是"梳理完了"。
