## 零、怎么用

1. **每个里程碑结束时**过一遍第三章对应小节，全绿才能进下一个。
2. **每条必须能明确判定通过 / 不通过**，不允许「看起来还行」这种结论。
3. 不通过的按第二章分级处理，不要当场凭感觉决定修不修。
4. 原型阶段允许与设计稿存在差异，但**必须记录在差异清单里**（见 4.9），不记录的差异等于缺陷。

## 一、缺陷分级

| 级别 | 定义 | 处理 |
|---|---|---|
| **Blocker** | 阻断后续开发或推翻架构前提 | 立刻修，不许进下一里程碑 |
| **Major** | 功能缺失、视觉明显偏离、违反硬约束 | 本里程碑内必须修 |
| **Minor** | 细节偏差（1~2px、过渡时长、文案） | 记入差异清单，M5 统一处理 |
| **Note** | 已知且有意的差异 | 记入差异清单，注明原因 |

**一条经验**：一旦开始写 `dark:` 变体或硬编码色值去绕过令牌，就是 Blocker —— 这会让深色变成要单独维护的第二套样式，正是第 9 轮「改完更乱」的根源。发现问题就去修令牌。

## 二、全局硬约束

贯穿所有里程碑，任何时候违反即不合格。

| # | 约束 | 检查方法 | 级别 |
|---|---|---|---|
| G1 | 颜色来源唯一，组件无 `#hex` / `rgb()` | 全局搜索十六进制色值，命中应**仅**出现在 `styles/tokens.css` | Blocker |
| G2 | 无 `dark:` 变体补丁 | 全局搜索 `dark:` | Blocker |
| G3 | 深浅两模式下所有文字可读 | 逐屏切换主题，检查正文对比度 ≥ 4.5:1、辅助文字 ≥ 3:1 | Blocker |
| G4 | 图标统一用 `--icon-neutral` | 抽查 5 个图标的 `stroke` 计算值，应均为 `#8A919E` 且**不随主题变化** | Major |
| G5 | 不使用 Tailwind 内置调色板 | 搜索 `bg-gray-` / `text-black` / `bg-white` 等 | Blocker |
| G6 | 无意外横向滚动条 | 各屏检查 `document.body.scrollWidth <= clientWidth` | Major |
| G7 | 交互元素键盘可达 | Tab 遍历，焦点环可见；按钮可 Enter/Space 触发 | Major |
| G8 | 折叠 / 展开有过渡，非瞬间跳变 | 目测，约 180ms | Minor |

> **G8 与 `prefers-reduced-motion` 的关系（2026-09-21 补充，勿再踩坑）**
>
> 不要给折叠写 `motion-reduce:transition-none`。它生成的是
> `@media (prefers-reduced-motion: reduce) { transition-property: none }`，
> 会把过渡**整个取消**，直接违反 G8 与验收 1-10 —— 而且 headless Chrome 默认就是 `reduce`，
> 一跑验收就挂，报错还看不出原因。
>
> 也**不要**因此就放弃 reduced-motion 适配（那是真实用户会遇到的场景）。
> 正确做法是**缩短时长而非取消过渡**：正常 180ms，reduced-motion 下用
> `COLLAPSE_DURATION_REDUCED`（**90ms**，即正常时长的一半）。这样两个目标同时达成：
> 验收要的「非瞬间跳变」保住，用户偏好也被尊重。
> 参考实现：`lib/use-prefers-reduced-motion.ts`。
>
> ⚠️ **不要把这个值缩到 `1ms`**（本文档早期误写过 1ms）：1ms 在 60fps 下不到一帧，
> rAF 采样中间帧数为 **0**，等价于瞬间跳变，1-10 照样挂 —— 那只是把「取消过渡」
> 换成了「快到看不见」，并没有真正满足要求（实测记录见 `progress-M1.md` 5.3.1）。

**G1 的检查命令**（在 `packages/ui` 下）：

```
搜索模式：#([0-9a-fA-F]{3,6})\b
范围：src/
预期：仅 styles/tokens.css 命中，且其中允许 --icon-neutral 存在
```

### M1 · 布局骨架

| # | 验收项 | 判定标准 |
|---|---|---|
| 1-1 | 三栏结构成立 | 侧边栏 / 内容区 / 预览区三栏并排，可用 flex 从 DOM 结构确认 |

| 1-4 | 条带高 36 | DevTools 量高度 = 36 |

| 1-7 | 历史会话无日期分组 | 不应出现「今天 / 昨天」分组标题 |

| 1-9 | 左右栏可折叠 | 点标题栏两端按钮对应栏收起 |
| 1-10 | 折叠有过渡且无跳动 | 宽度过渡约 180ms；折叠过程中内容区不出现闪跳或重排错位。**判定必须看中间帧**：rAF 采到 ≥3 个中间宽度值才算「非瞬间跳变」，只读 `transition-duration` 不算 |
| 1-11 | 折叠状态持久化 | 刷新后保持 |
| 1-12 | 全屏后内容填满 | 两栏都收起时内容区宽 **== 视口宽（1424）**，无横向滚动条 |
| 1-13 | 折到 0 宽时严格为 0 | 折叠态 `getBoundingClientRect().width === 0`（**不是 1px**）；两栏全收起时内容区宽 == 视口宽 |

> ⚠️ **判定必须产出显式断言，不能只打印数值。**
> 1-12 / 1-13 曾被"只记录不断言"的写法放过：脚本把 `sidebar: 1`、`workspace: 1422`
> 印在输出里，脚本本身 EXIT=0，看起来"全绿"，但**没有任何 pass/fail 判断** ——
> 「没有失败」被误当成了「通过」。既然要求严格 0，断言就必须是
> `=== 0` / `=== 1424`，且要**汇总成布尔结论**。相关机制见 `task-M1.md` 第 3.4 节。

> 1-3 是整个 M1 最容易做错的一项。设计稿第 11 轮才把通底定稿，实现时很容易残留 12px 内边距或圆角。

## 六、验收流程

```
自测 → 对照设计稿 → 记录差异 → 分级 → 修复 → 复验 → 签字放行
```

1. **自测**：跑本节第二章全局约束，先清 Blocker。
2. **对照**：按第四章逐屏打勾。
3. **记录**：所有偏差进差异清单，哪怕只是 1px。
4. **分级**：按第一章定级，不要凭感觉。
5. **修复**：Blocker / Major 当轮清，Minor 攒到 M5。
6. **复验**：改完重新跑受影响条目，不是改了就算过。

## 八、一句话总结

**这份验收标准真正在守的东西只有三条**：

1. 颜色只能有一个来源（`tokens.css`）
2. 深色不许有独立代码
3. 每个偏差都要被记录，而不是被遗忘

其余都是具体数值的对齐。前三条守住了，后面设计稿再改 12 轮也不会失控。
