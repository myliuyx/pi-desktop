## 四、模型接入方式（可复用）

火山方舟作为自定义 provider 走 `models.json`（`~/.pi/agent/models.json` 或 `ModelRuntime.create({ modelsPath })` 指定）：

```json
{
  "providers": {
    "ark-coding": {
      "baseUrl": "https://ark.cn-beijing.volces.com/api/coding/v3",
      "api": "openai-completions",
      "apiKey": "$ARK_API_KEY",
      "compat": { "supportsDeveloperRole": false, "supportsReasoningEffort": false },
      "models": [{ "id": "deepseek-v4-flash" }]
    }
  }
}
```

要点：

- **`/api/coding/v3` 是 Chat Completions 端点**（Anthropic Messages 端点才是 `/api/coding`，不带 `/v3`），
  所以 `api` 必须填 `openai-completions`。
- `apiKey` 用 `"$ARK_API_KEY"` 环境变量插值，不落明文到文件。
- 兼容端点一般不认 `developer` 角色与 `reasoning_effort`，先关掉 `compat` 两项，避免第一步撞在协议差异上。
- SDK 侧：`ModelRuntime.create({ modelsPath })` → `setRuntimeApiKey(provider, key)` →
  `getModel(provider, id)` → `createAgentSession({ model, modelRuntime })`。
  `pi-ai` 的顶层 `getModel()` 已标记 deprecated，应走 `ModelRuntime` 实例方法。

## 五、踩过的坑（每条都可复现，别再踩）

1. **npm 官方源在这台机器上等于卡死。** 单次元数据请求 `registry.npmjs.org` **10987ms** vs
   `registry.npmmirror.com` **340ms**。首次 `npm install` 跑了 26 分钟零进展（node_modules 条目数与日志
   mtime 双双冻结）——**"慢"和"卡死"要区分，判据是进度是否还在变化**。
   换源后 1 秒完成：`npm install --registry=https://registry.npmmirror.com`。
   判卡死的办法：隔几分钟数一次 `node_modules` 条目数 + 看日志 mtime。
2. **Electron 的 `npm install` 不下载二进制。** 只装了 JS 包装，`dist/` 不存在。
   必须手动 `node node_modules/electron/install.js`，配 `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/`
   后 7 秒下完。
3. **宿主环境继承了 `ELECTRON_RUN_AS_NODE=1`**（WorkBuddy 自身是 Electron 应用），
   导致 `electron.exe` 退化成纯 Node，`require("electron")` 只返回路径字符串、`app` 为 undefined。
   跑之前必须 `unset ELECTRON_RUN_AS_NODE`。
4. **无显示环境下 Electron 会被 GPU 进程崩溃带走**（`GPU process isn't usable. Goodbye.`），
   这与 Pi 无关。加 `--disable-gpu --disable-software-rasterizer --disable-gpu-sandbox --no-sandbox` 即可。
5. **Electron 主进程别用 ESM 具名导入**：`import { app } from "electron"` 报
   `does not provide an export named 'app'`。改 CJS（`main.cjs` + `require`）即可。
6. **Windows 下 GUI 进程 stdout 可能不回传**——探针结果要同时写文件，否则看不到输出。
7. `HUSKY=0` 可跳过 Pi 的 husky prepare，避免把它的 git hooks 装进我们的仓库。

## 六、遗留与边界（本次未覆盖）

1. **asar 打包未验证。** POC 跑的是未打包的 Electron。真正的风险（native `.node` 在 asar 内无法 dlopen）
   要到打包阶段才暴露。缓解手段现成：asar 拆包（`--unpack`）或 `asarUnpack` 配置。
   **修订（2026-09-23）**：部署形态已裁决为「**本地服务 + 浏览器**，不涉及云端」（见
   `survey/S4-transport-decision.md` §八），**Electron 降级为可选外壳** ——
   因此本条风险**不再位于关键路径上**：core 是普通 Node 进程，不经过 asar 打包。
   仅当将来决定保留 Electron 外壳时才需重新评估。同理，本文档 §二 表格里的 Electron 相关条目
   与 §五 的坑 2/3/4/5（Electron 安装、`ELECTRON_RUN_AS_NODE`、GPU 崩溃、CJS 导入）
   都只在保留外壳时才有意义。
2. **用的是源码 monorepo（workspace 软链），不是 npm 发布包。** 仓库内
   `packages/tui/native/win32/prebuilds/` 为空（`.node` 是构建产物），而 npm 发布包自带 prebuilds。
   本次实测 monorepo 下 `@earendil-works/pi-tui` 与 `photon-node` **模块导入均成功**，
   但「native binding 是否真的被 dlopen」未做更深探测——pi-tui 的 binding 可能是运行时懒加载。
   接 npm 包时应重跑一次本探针确认。
3. **只跑了纯文本会话。** 未验证工具调用（bash / read / edit）、授权卡片、执行计划等 Pi 事件，
   这些是适配层阶段的事。
4. **密钥存放**：`pi/_poc/.env.local`（`pi/` 整体已 gitignore，未入库）。如介意可轮换该 key。
