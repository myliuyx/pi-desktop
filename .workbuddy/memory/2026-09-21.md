## 踩坑记录

- `C()` 复制时用 `descendants` 覆盖子节点常失败（Copy descendant not found）；改用实例分号路径 `U("instId;childId", …)` 更稳。
- `batch_edit` 的 binding 名仅在同一批内有效，下一批必须用返回的真实 ID，否则整批 `parent not found`。
- 一次 batch_edit 控制在 ≤25 ops；大结构分批插。
- `capture_layout` 的 parentId 不能是 page（`0:1`），必须传具体顶层 frame。
- 网络偶发 `ECONNRESET`，重发即可。
- `LARGE_EMPTY_AREA` 多为预期留白，需结合设计意图判断，不要盲目填满。
- **SVG 图标必须用 `viewBox="0 0 16 16"` 配 width/height 16**。用 24 viewBox（如 Feather 14×14/24×24 图标）解析会出错：产生越界的 100×100 白色「Frame 1」垃圾节点，图标位置也跑偏。修复：删垃圾节点 + 用 16 viewBox 重画。
- 换 SVG 图标的流程：`D` 旧图标 → `I` 新图标（会追加到末尾）→ `M(newId, parentId, 0)` 移到首位。
- 固定高度容器改竖排多行时容易忘记改 height：容器 height 40 + 子项 `height:"fill_container"` 会被压成 15px，导致图标/文字 `OUTSIDE_PARENT`。修法：容器 `height:"hug_contents"` + 子项给固定高（如 32）。

## 进入实现阶段 · 技术方案推荐（待用户确认）

- 用户决定开始落地，先做页面。本轮给出分层架构建议（壳层 / UI 层 / 状态与数据层 / Agent 运行时）。
- 核心建议：**先在浏览器里做纯前端原型**（Vite dev server + mock 数据），设计定稿后再套桌面壳。理由：设计已迭代 12 轮仍会改，浏览器 HMR 迭代成本远低于桌面壳重载；前端代码 ~90% 可复用，壳层只影响约 10%。
- 壳层二选一：
  - 倾向 **Electron**——Agent 类重度依赖 Node 生态（@modelcontextprotocol/sdk、Vercel AI SDK、node-pty 均 TS/Node 优先）；Tauri 需 sidecar 打包 Node，体积优势被抵消且多一层 IPC。代价：包体 150MB+、常驻内存 200~400MB。
  - 选 **Tauri 2** 的前提：包体/内存是核心卖点且团队有 Rust 能力。包体 10~15MB、内存 60~120MB；Linux 依赖 WebKit2GTK。
- 前端栈建议：React 19 + TS + Vite + Tailwind v4；组件用 Radix/shadcn（headless 自套令牌，不用 AntD/MUI 以免风格打架）；Zustand + TanStack Query；@tanstack/react-virtual；react-markdown + Shiki；xterm.js；better-sqlite3 + Drizzle。
- 令牌落地方案：CSS 变量（`--bg-app`/`--bg-subtle`/`--border-subtle`/`--text-primary`）对应 Figma 变量集 `Theme`（Light 3:1 / Dark 3:3），深浅切换靠根元素 `data-theme`；Tailwind v4 用 `@theme inline` 映射。Radius 变量集同理。

### 补充：后期要加 Web 版

- 用户提出后期可能要做 Web 版 → 架构必须按 C/S 前后端分离设计。
- **硬约束：UI 层禁止 import 任何 `node:*`（fs / child_process / node-pty），只能走统一 transport 接口。**
- monorepo（pnpm workspace）结构：`packages/core`（Agent 运行时，Node 环境）、`packages/ui`（React 前端，纯浏览器）、`packages/desktop`（壳）、`packages/web`（HTTP + SSE server）。
- transport 统一方案：桌面版也在 `127.0.0.1` 起本地 HTTP + SSE server，前端代码与 Web 版完全一致（需处理端口占用 + 本地 token 校验）。
- 对壳层的影响：C/S 架构下 Tauri 劣势被削弱（Node 全关在 core 里，Tauri 只管 sidecar 拉起 + WebView），但 Node 二进制仍要打包，体积 10MB → 60~100MB。Electron 仍最省心（core 直接在 main process import，无 sidecar / 无端口管理）。
- **最终建议：Electron + 严格 C/S 分层。**
- 风险提示：Web 版无法与桌面版功能等价——文件系统与真实终端是桌面独有能力。Web 版要么功能裁剪，要么配云端沙箱（成本高）。此决策会反向影响 core 接口设计，需尽早定。

## Pi 作为 Agent Core 的可行性调研（已 clone 到 ./pi，未 npm install）

仓库：earendil-works/pi（作者 Mario Zechner / badlogic），MIT，v0.86.1，pre-1.0。npm 包每几天一版。

### 包结构（workspaces）

`chord`（组合运行时/RPC/复制状态）、`ai`（统一多供应商 LLM API）、`agent`（= pi-agent-core，Agent 循环）、`coding-agent`（CLI + SDK）、`tui`（终端 UI，有 win32/darwin/linux native）、`durable`、`telemetry`、`protocol` / `client` / `server`（**均为 experimental，无兼容保证**）、`session-backends/sqlite-node`。

### 结论：可行，且契合度高

- **用 `pi-coding-agent` 的 `createAgentSession()`，不要用裸的 `pi-agent-core`。** 前者自带 read/bash/edit/write 工具、SessionManager、ModelRuntime（OAuth + API key）、SettingsManager、扩展与 skills 系统；后者只是循环，工具要自己写。
- **Electron 集成走主进程直接 import**（rpc.md 明确建议 Node 应用优先用 AgentSession 而非 spawn 子进程）。主进程 → preload contextBridge → 渲染进程。后期 Web 版改成 Node server + SSE，UI 侧 transport 接口不变。
- **Electron 版本兼容**：Electron 43.3.0 带 Node 24.18.1 / 42.11.1 带 Node 24.19.0，均远超 pi 要求的 `node >=22.19.0`。

### 设计稿 UI 元素 ↔ Pi API 映射（一一对应，契合度很高）

| 设计稿元素 | Pi 侧能力 |
|---|---|
| 消息流流式渲染 | `message_update` 的 `text_delta` / `thinking_delta` / `toolcall_delta` |
| 终端步骤卡片 | `tool_execution_start` / `_update`（累积 partialResult）/ `_end`；bash 输出流式 |
| Token 信息组（输入/输出/消耗/上下文） | `get_session_stats` → tokens.input/output/total + contextUsage.tokens/contextWindow/percent |
| 思考强度芯片 Low/High/Max | `set_thinking_level`：off/minimal/low/medium/high/xhigh/max |
| 模型芯片 | `get_available_models` / `set_model` / `cycle_model` |
| 技能芯片 | `get_commands`（extension/prompt/skill 三类） |
| 授权卡片 | Extension UI Protocol：`select` / `confirm` 请求-响应，示例即 "Allow dangerous command?" → ["Allow","Block"] |
| 历史会话 | SessionManager + `get_tree` / `get_entries`（游标增量）/ `fork` / `clone` / `switch_session` |
| 停止按钮 | `abort`；中断指令用 `steer`，追加指令用 `follow_up` |

### 必须自己补的部分（作者明确的设计立场）

- **没有内置 MCP**——`usage.md` 原话："intentionally does not include built-in MCP, sub-agents, permission popups, plan mode, to-dos, or background bash"。设计稿里的「MCP」芯片要自己用 extension + `@modelcontextprotocol/sdk` 实现（转成 AgentTool）。
- 授权弹窗、plan mode、to-dos、background bash 同样没有内置，需用 extension 实现（授权卡片走 Extension UI Protocol 即可）。
- Pi 无内置权限系统，默认以启动用户权限运行；强隔离需容器化（Gondolin / Docker / OpenShell）。

### 风险

- pre-1.0（0.86.1），发布极频繁，API 可能变。
- `protocol` / `client` / `server` 三包 experimental 且无兼容保证——但 Electron 主进程直连方案不依赖它们，可绕开。
- `docs/mobile-handoff` 自述：7 个单元中 3 个有可用代码、4 个仅规格；`04-tool-output` / `05-assistant-output` 未实现；typecheck 基线 ~788 已有错误。属内部重构计划，不直接影响 SDK 使用。
- coding-agent 依赖 pi-tui（含三端 native 模块）与 photon-node wasm，Electron 打包时需验证 native 依赖能否正确打进 asar。
- 当前 clone 未执行 npm install，也无 dist，跑起来需先在 pi 目录 `npm install --ignore-scripts && npm run build`（ai 包构建需联网拉 model data）。

## 追加：4 个缺陷的修法复审 —— 上面第 3、4 条的结论被推翻

### 缺陷 4（折叠残留 1px）—— 两轮都没修对，第三轮才定稿

- **agent 的修法（折叠时把 `border-*-width` 置 0）**：能达到 0 宽，但改 `border-width`
  不参与 `width` 过渡，会在过渡收尾闪一下边框。**我否决了它。**
- **我的修法（`min-w-0`）**：**实测无效**。写了诊断脚本 `scripts/m1-diagnose-zero.mjs`
  逐层量取，四层容器 `min-width` 全为 `0px`，折叠后仍卡在 1px、内容区仍 1422。
- **真根因（实测确认）**：`box-sizing: border-box` 下**边框盒不可能窄于边框自身**。
  实测把内联 `width` 依次设为 `0` / `0.5` / `1` / `2` / `10px`，`rect` 宽度**恒为 1px**。
  `min-width` 管收缩下限，管不了边框的物理宽度 —— 这是条硬下限。
- **定稿修法**：分隔线从 `border` 换成**绝对定位伪元素**，在 `globals.css` 加
  `divider-r` / `divider-l` 两个 `@utility`。伪元素脱离常规流、**不占布局宽度**，
  父元素才能真正收到 0；也因为没有 `border-width`，"收尾闪边框"的副作用自然消失。
- **实测**：折叠后 `sidebar = 0`、`workspace = 944`、两栏全收 `workspace = 1424` == 视口宽、
  `workspace_left/right = 0/1424`、条带宽 `264`（原 263）。

### 缺陷 3（`motion-reduce` 取消过渡）—— agent 的"移除适配"被推翻

- **agent 的修法**：直接移除 `motion-reduce:transition-none`，理由是"规格优先级高于 a11y 惯例"。
  **这把冲突藏了，没真做适配**，而且"必须二选一"这个前提本身是错的。
- **定稿修法**：新增 `lib/use-prefers-reduced-motion.ts` 侦测偏好，
  时长改为 `prefersReducedMotion ? COLLAPSE_DURATION_REDUCED : COLLAPSE_DURATION`。
- **踩坑**：初版 `COLLAPSE_DURATION_REDUCED = 1`，实测 rAF **中间帧数 = 0**
  （`264 → 1` 直接跳），1-10 照样挂 —— 1ms 不到一帧，只是把"取消过渡"换成"快到看不见"。
  改 **90ms**（正常的一半）后中间帧数 **4**，序列 `264 → 138.7 → 72.36 → 32.48 → 10.2 → 0.77 → 0`。

### 我自己的复核也出过错（值得记住）

- 第一次复核我写"4 个缺陷修复均属实且修法正确"，**只重跑了验收脚本看结论，
  没质疑修法机制本身**。而当时脚本对 1-12 / 1-9 两段**只 print 数值、没有任何 pass/fail 断言**，
  `sidebar: 1 / workspace: 1422` 就这么印在输出里、"脚本没报错"被我当成了"通过"。
  是注意到"1422 ≠ 1424"这个绝对差值才揪出来。
- **教训一：验收脚本必须给显式断言，不能只打印数值让人眼比对。**
  「没有失败」和「有断言且通过」是两回事；EXIT=0 只代表脚本自己没崩。
- **教训二：断言本身要反向验证。** 我把修复前的坏数据 `(1,1,1422,1424)` 喂进新断言，
  确认它判 `false`；再喂修复后的 `(0,0,1424,1424)` 确认判 `true`。

### 新增经验
