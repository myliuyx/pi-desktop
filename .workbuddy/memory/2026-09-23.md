## 追问：做 Web 版会麻烦多少？

**三条 grep 实证（可直接复用，不必重查）：**

1. `packages/ui/src` **零 `node:*` / electron / ipcRenderer**。全量命中只有
   `navigator.clipboard`（`components/shell/PreviewPane.tsx:190`）与 `window.localStorage`
   （`store/ui-store.ts` L32/39/45/58/95/182/191/212/238/273）—— **两者浏览器原生可用**
   → 结论：UI 层 8 屏六路由**一行不改**即可跑在浏览器，这是 S4 选 B 的回报。
2. `components/shell/TitleBar.tsx:57-78` 的 `WindowControls` 是**纯展示**（外层 `aria-hidden="true"`、
   三个 span 无 onClick），mac 用 `MacTrafficLights`、win/linux 用内联 SVG `WindowControlGlyph`
   → Web 版**隐藏即可，不涉及功能迁移**。
3. `packages/` 下**只有 `ui` 一个包，`core` 尚未创建** → 现在拍板零返工。

**成本分层结论：**
- 免费：`packages/ui`；`AgentTransport` 接口（S4 已按 B 定，桌面/Web 只换 baseUrl 与鉴权）
- 新增（core 侧）：安全模型重做（本地版「随机端口 + 一次性 token + 拒绝跨来源」三件套在 Web 版全废，
  换成多用户身份 + 会话级鉴权 + CORS/CSRF/限流 + 多租户隔离）；凭据与算力归属（key 不能下发浏览器、
  谁付 token 钱、`~/.pi/agent/` 从单用户目录变每用户隔离存储 —— **直接改 S2 的答案**）
- 决定性未知：**「用户的文件在哪」**。桌面版立足点 = Pi 跑本机、读写用户真实项目目录；
  上云后三条路：a 云端容器（= 新产线，对标 Devin/Codex Cloud）/ b 浏览器跑 Pi（不可行，
  Pi 依赖 bash + native `.node`，且 S1 实测 Windows 下 bash 工具本就报 `No bash shell found`）/
  c 本机 daemon + Web 当遥控器（本质仍是桌面版，共享同一套 core，增量最小）。
  **a 与 c 之间是数量级差异，选定前给不出可信工时。**

**拍板时机建议**：S3 不受影响可照做；**S2 之前必须拍**（会话存哪依赖它）；硬 deadline = 动
`packages/core` 实现之前（= S4 第八节待定项 1 自己留的话）。

用户明确：「Web 版」= **本地起一个服务 + 浏览器访问**，**不涉及云端**；不绑 `0.0.0.0` 时只本机可访问，

  直接消失；主进程 import 成本 887ms、Electron 44.4.3 / ABI 149 绑定都不再是约束。
  core = 普通 Node 进程 + 静态前端。**此项需用户确认（桌面壳是否仍要）**
- **验收体系原样继续**：accept:m1~m5 / probe-r7 本就是 CDP 驱动真实浏览器，架构不变

  （`aria-hidden` + 无 onClick），隐藏即可

**唯一真正新增的攻击面**：浏览器里任意网页都能请求 `127.0.0.1`（Electron IPC 方案没有 HTTP 端口，故无此问题）。

`0.0.0.0` 面 = 同局域网任何人可连，token 须够强且可撤销，内网明文 HTTP 有嗅探风险（需 HTTPS 或显式接受内网可信）。

## S2 会话持久化 收尾（2026-09-23 第四轮）

产物 `survey/S2-sessions.md`，**远短于原估 3h**。

**核心发现：Pi 把会话持久化整个做好了，我们不用自建存储。**
`core/session-manager.ts` 的公开静态方法：`list(cwd,…)`（L1758）/ `listAll(…)`（L1779）/
`open(path,…)`（L1624）/ `continueRecent(cwd,…)`（L1651）/ `findById(cwd,id,…)`（L1732）/
`create`（L1613）/ `forkFrom`（L1673）；实例侧 `getSessionName()`（L1226）等。
会话自动存 `~/.pi/agent/sessions/<encoded-cwd>/`（`usage.md:79`）。

**字段映射**：`SessionInfo{path,id,cwd,name?,parentSessionPath?,created,modified,messageCount,firstMessage}`
（`session-manager.ts:196-208`）→ 我们的 `SessionSummary{id,title,updatedAt,messageCount}`（`types.ts:135`）
**四字段全有来源，不用改类型**。建议 `title = name ?? firstMessage`；`updatedAt` 要显式把 `Date` 转 epoch ms。

**★ 原估里没有的新增工作量**：**「加载历史会话」与「重放实时事件」是两条不同路径** ——
会话文件里存的是 **`SessionEntry[]`**（另一种形状，`session-manager.ts:165`），
需要独立写 `SessionEntry[] → Message[]` 映射；`adapter/reduce.ts` 的**实时事件 reducer 不能复用**。
还要处理：entry 是**树结构**（Pi 支持 `/tree` `/fork` `/clone`，原型无分支 UI → **待拍板**）、
非消息类 entry（`UsageEntry` 可喂 `TokenUsage`）、`CustomMessageEntry.display`。

### ★★ 两条新增必须裁决项（建议 core 实现前拍掉）

1. **⚠️ 安全：项目本地扩展被自动加载执行，未见信任交互。**
   spike 只给 1 个扩展却报 **5 个** —— 多出的 4 个来自 **`pi/.pi/extensions/`**
   （`import-repro.ts` / `prompt-url-widget.ts` / `redraws.ts` / `tps.ts`），
   因为 `cwd` 落在 `pi/` 被当作**项目本地扩展**加载（`sdk.md:347`）。
   但 `usage.md:121-127` 说项目本地资源需要信任、非交互模式按 `defaultProjectTrust`
   （默认 `ask` 会忽略）—— **本次是直接加载了，没任何交互或报错**。
   扩展是**可执行代码**，而我们的形态是「用户在自己机器上起服务 + 浏览器访问」
   → **在任意含 `.pi/extensions/` 的仓库里打开我们的 app 就会加载执行**。
   待归因（SDK 本就不走信任门？还是 settings 恰为 `always`？）。
   处置二选一：**加 UI 信任确认** 或 **不加载项目本地扩展（只认全局 `~/.pi/agent/extensions/`）**。
2. **产品：拒绝授权后模型会换写法反复重试。** 实测连拒 4 次，模型换了 4 种命令写法
   （`ls | head -3` → `ls -1 | head -n 3` → `find . -maxdepth 1 …` → `pwd`），
   烧 5–6 个 turn。**「拒绝」当前是循环起点而不是终点。** 需「拒绝并停止」选项，
   或先确认 `block.reason` 是否进了模型上下文。

### ★ 方法论教训（新，与既有 #1 同族但方向相反）

### S3 实测发现（全部源码实证，带 `文件:行号`；**未跑真实 dump**）

1. **★ 授权通道的真实形态被推翻重写**：不是「消费 Pi 的 `extension_ui_request` 事件」，
   而是 **core 实现 `ExtensionUIContext` 接口**。
   证据：`core/extensions/types.ts:130-133` 原文「Each mode (interactive, RPC, print) provides its own
   implementation」；`rpc.md:1186` 说 `extension_ui_request` 是
   「request/response sub-protocol **on top of** the base command/event flow」。
   → **S1 §八「rpc.md 事件表里没有它」需修正**（它在 `rpc.md` L1186-1340 独立小节、
   `rpc-types.ts:241-291` 有完整 9 变体类型，只是不在基础事件表内）。已回写 S1 并标注。
   注入点：`session.bindExtensions({ uiContext, mode })`（`agent-session.ts:2610-2614`，

2. **★ `hasUI` 陷阱**：`runner.ts:530-532` 的 `hasUI()` = `uiContext !== noOpUIContext` ——
   **不是我们声明的，是「是否注入」推导出来的**。而 `permission-gate.ts:20-23` 在 `!ctx.hasUI` 时
   直接 `return { block: true }` → **漏注入 = 危险命令静默失败且 UI 无任何授权卡**。
3. **★ 工具授权由 extension 提供，非内核内置**：`grep` 确认 `coding-agent/src` 里
   没有 `requiresApproval|permission|autoApprove` 等任何内置授权机制；授权示例是
   `examples/extensions/permission-gate.ts`（`pi.on("tool_call")` + `ctx.ui.select` + 返回 `{block:true}`）。
   → **不启用此类扩展，`ApprovalCard` 永不出现**（产品级前提）。
4. **幂等语义两边天然一致**：`rpc-mode.ts:776-781` 是 delete-then-resolve，
   重复/未知/过期 id **静默丢弃不报错**；`rpc-mode.ts:103-107` 的 cleanup 超时/abort 也清 id。
   ↔ 我们 `resolveApproval`「已决 requestId 不覆盖」同为 first-write-wins + 静默。**不需要改语义**。
5. **超时由 Pi 侧管，但 UI 仍须自兜底**：`rpc-mode.ts:115-120` 有 timeout 时
   `setTimeout(→ cleanup + resolve(defaultValue))`；`rpc.md:1193` 明说「client does not need to track
   timeouts」。但超时后 id 已被移除 ⇒ **用户再点会被静默丢弃、表现为"点了没反应"**
   → UI 必须自己渲染倒计时/失效态。
6. **Pi 不回显授权结果**：`permission-gate` 的结果是 **hook 返回值**不是事件 → 不会下发任何东西
   → `ApprovalBlock.resolved` **只能是 UI 侧乐观写入**（现有 mock 行为恰好正确）。
   连带未验项：用户拒绝后 UI 看到的终态是什么（无 `tool_execution_start`？还是 `isError` 结果？）。
7. **终端卡片字段来源定位**：`command` ← `tool_execution_start.args.command`；
   `output` ← `_update.partialResult` → `_end.result.output`；`exitCode` ← `_end.result.exitCode`
   （`BashResult` 定义在 `core/bash-executor.ts:29-40`，另有 `cancelled` / `truncated` / `fullOutputPath`）。
   **⚠️ 我们的 `adapter/pi-events.ts:38-40` 的 `tool_execution_end` 丢掉了 `exitCode` 与 `truncated`**，
   `TerminalBlock` 有这两个字段却没人填。
   坑：**同一个「命令」在 Pi 里有两套字段名** —— `tool_call` hook 是 `event.input.command`
   （`permission-gate.ts:16`），`tool_execution_*` 是 `event.args.command`。
8. **两个真实缺口**：① `hiddenLineCount` Pi 不提供（只给 `truncated: boolean`）；
   ② **`fullOutputPath` 在浏览器里没有出口** —— Pi 给的是本机临时文件绝对路径，
   客户端是浏览器读不到 → 需要 core 新增 `GET /tools/:toolCallId/full-output` 之类端点。
   这是原型期不存在、验收 2-7「查看完整内容」要求的真实工作量。
9. **`ApprovalBlock` 字段核对结论：够用，不需要改结构**（`options: string[]` 与

   是我们照 `rpc-mode.ts:99` 的 `crypto.randomUUID()` 自己生成。
   另登记一条待拍板的 UI 细节：`permission-gate.ts:25` 把命令原文塞进 `select` 的 **多行 title**
   （`\n\n` 分隔），我们的 `ApprovalCard` 整块渲染还是拆出等宽代码块？（涉及组件，本轮不动）
10. **取消应答建议另开方法**：`resolveApproval(requestId, choice)` 签名冻结（M2），
