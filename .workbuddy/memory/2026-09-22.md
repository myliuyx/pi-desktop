### ★ 本轮踩的三个大坑（重要，别再踩）

**坑 2：照单全收了别人（错误）的根因判断。** Agent B 先遇到同一现象，判断是"缺 `--remote-allow-origins=*`"。

→ **教训：别人的根因结论也是"待验证假设"；越是"补个参数就好"这种低成本建议，越容易跳过验证。**
验证它需要的是**能区分多个假设**的诊断，而不是再跑一遍原脚本。

**坑 3：首版验收脚本自己有 7 处缺陷，制造了 7 个"假失败"。** 首轮 10 个失败里
**7 个是脚本写错、1 个是级联**，真缺陷只有 2 个。清单（都是很容易重犯的）：

| 写法 | 后果 |
|---|---|
| 探针函数只取 `getComputedStyle().color` | 用 `bg-*` 类做探针时拿到的是继承文字色 → 颜色断言恒假（需单独写 `probeBg` 取 backgroundColor） |
| 读 `getComputedStyle().width`（`"28px"` 字符串）做减法 | `NaN` → 尺寸断言恒假（要读 `getBoundingClientRect()` 的数字） |
| 断言引用了**下一个代码块**的同名变量 `r` | `undefined >= 1` 恒假 |
| `async IIFE` 调 `cdp.eval` 时**漏传 `awaitPromise=true`** | `returnByValue` 把 Promise 序列化成 `{}`，断言全 undefined，日志里只看到空对象 |
| 正则写成 `/还有\\s*\\d+行/`（在普通 JS 里，不在模板字符串内） | 变成匹配字面反斜杠 |
| `querySelector('[data-testid="markdown-body"]')` 只取第一个 | ThinkingCard 也渲染 markdown-body，命中的是思考块 → 误判"标题/列表/表格/链接都没有" |
| 断言"滚动后 scrollTop 应变大"，假设从顶部开始 | 但列表**会自动贴底**，起点本就在底部 |

→ **教训：失败的断言要先怀疑断言本身。** 不逐条抠原始数值，就会让实现方去修不存在的问题。

### 本轮修掉的两个真缺陷（都在 Agent A 的实现里，它被中断没自验）

1. **【Major】终端输出溢出而非滚动**：`terminal-output` 只设 `maxHeight` 没设 `overflow`，
   实测 `overflow-y = visible` → 展开完整内容后会溢出到卡片外。修法：加 `overflow-auto`。
2. **【Major】自动贴底不收敛**：点「回到底部」后实测 `dist = 134`（阈值 32）。
   根因：列表高度是**动态测量**的，程序化滚到底后列表继续长高 → 紧接着的 scroll 事件算出"没贴底"中间态 →
   把 `atBottom` 翻成 false → 而补滚用的 `ResizeObserver` **只在 atBottomRef 为真时才补滚** → 再没人纠偏，卡死。
   **即：一次瞬时错位把"自动贴底"永久关掉了。**
   修法（`MessageList.tsx`）：加 `pinningRef` 区分「程序化贴底」与「用户上滚」；贴底过程中的非贴底中间态
   继续补滚、不翻状态；只有真实用户交互（wheel/touchstart/keydown）才允许退出自动贴底；`scrollToBottom` 补两帧 rAF。

## Pi 模型配置体系调研（回答「我们能不能全继承 Pi 的接模型方式」）

**结论：能全继承，而且应该全继承——不要自造一套模型配置。**

Pi 的三层（默认全在 `~/.pi/agent/`，SDK `createAgentSession()` 默认就读它，
所以用户已装的 Pi CLI 配置我们打开即用）：

| 文件 | 职责 | 关键字段 |
|---|---|---|
| `models.json` | 有哪些模型、端点在哪 | provider `baseUrl` / `api`(openai-completions\|openai-responses\|anthropic-messages\|google-generative-ai) / `models[]` / `compat` / `modelOverrides` |
| `auth.json` | 凭据（key 或 OAuth） | 由 `setRuntimeApiKey()` / `login()` 写入 |
| `settings.json` | 当前选哪个 | `defaultProvider` `defaultModel` `defaultThinkingLevel` `modelThinkingLevels`（按 provider/modelId 分别记） |

**grep 实证的 API（packages/coding-agent/src）**：
- 列模型：`modelRuntime.getAvailable(providerId?)` / `getModels(providerId?)` / `getProviders()`；
  凭据状态 `listCredentials()` / `getProviderAuthStatus(id)`
- 存凭据：`setRuntimeApiKey(providerId, key)`；OAuth：`modelRuntime.login(providerId, method, opts)`
- 运行时换：`session.setModel(model)` / `session.setThinkingLevel(level)`
- 持久化：`settingsManager.setDefaultModelAndProvider(provider, modelId)` / `getDefaultModel()` /
  `setDefaultModel()`（`settings-manager.ts` L738/748/754）
- ⚠️ `pi-ai` 顶层 `getModel()` 已 deprecated，走 `ModelRuntime` 实例方法

**★ 关键边界（读代码发现，别踩）**：`ModelRuntime.create()` 的 `modelsPath` **只有一个、不合并**
（`model-runtime.ts` L175-176：给了就用给的，否则 `~/.pi/agent/models.json`）。
→ **我们要内置火山方舟这类 provider，不能靠塞一份自己的 models.json**（会顶掉用户配置），
正路是写 Pi extension 用 `pi.registerProvider(name, config)` 注册（extensions.md L1777，
官方示例 `custom-provider-anthropic/`），它是叠加在内置 + models.json 之上的。

**我们 UI 的两个触点接法**：
- `ComposerToolbar` 的 ChipMenu 模型/思考菜单：选项从 `getAvailable()` 派生（按 provider 分组），
  替代 `mock/composer.ts` 的 `COMPOSER_MODELS` / `COMPOSER_MODEL_GROUPS`；选中走
  `session.setModel()` + `settingsManager.setDefaultModelAndProvider()`（与 05 屏共享同一真相）
- `SettingsScreen` 模型组：读写 settings.json 同一份，替代 `mock/settings.ts`
- 思考档位：Pi 是 `off/minimal/low/medium/high/xhigh/max` **七档**，我们 mock 是三档（Low/High/Max）
  —— 接真数据时要把档位表换成 Pi 的七档，UI 得能容纳更多项

**已落文档**：`.plan/pi-integration-points.md` 新增第七节（模型配置全继承 + registerProvider 边界）
与第八节（思考档位三档→七档的四个影响）；原「不动清单」顺延为第九节。
